# Delivery estate board

The Grafana board **Delivery estate** (`delivery-estate`, folder Boards) answers three questions
about every repository in the webgrip organisation:

1. Is it under control, and if not, what fixes it?
2. How does it build, release and ship?
3. Which version of each shared package does it run?
4. Where do pull requests wait, and on whom?

It is generated by [`scripts/dashboards/delivery.py`](https://forgejo.webgrip.dev/webgrip/homelab-cluster/src/branch/main/scripts/dashboards/delivery.py)
like the other boards ([information radiators](information-radiators.md)).

## Where the numbers come from

| Panel family | Source | Freshness |
| --- | --- | --- |
| Estate control, estate table, update state of behind pins, release style, shared package adoption, shared workflow calls, estate shape | `repo_config_*` series pushed by the repo-config inventory CronJob | hourly |
| Bottleneck queue, pile-up, PR counts, fan-out, release-to-PR wait, time to merge, dashboard ticks, releases | Forgejo's own database (`forgejo-db`) | live |
| CI queue wait | `forgejo-ci-exporter` | five minutes |

The inventory ([`repo_config_inventory.py`](https://forgejo.webgrip.dev/webgrip/homelab-cluster/src/branch/main/kubernetes/apps/repo-config/repo-config/inventory/repo_config_inventory.py))
already compared the organisation with the repo-config model. It now also reads, from each active
repository's default branch:

| File | What it yields |
| --- | --- |
| `renovate.json` (or `.json5`, `.renovaterc`, `.renovaterc.json`, `.renovaterc.json5`, and `.forgejo/` or `.github/` copies of `renovate.json` and `renovate.json5`: the list the model schema allows) | the Renovate gate (the `reviewed` or `unattended` preset it extends) and the `renovate-config` pin |
| `.forgejo/workflows/*.yml`, `.github/workflows/*.yml` | the `webgrip/workflows` pin of each reusable workflow and composite action call, which ones it calls, how it releases, what it publishes, and the `harbor.webgrip.dev/webgrip/semantic-release:<version>` toolchain image it runs in |
| `<path>/action.yml` of each local action a workflow calls (`uses: ./<path>`) | read as if its steps were in the workflow, so a release that runs inside a repository's own action still counts |
| `apm.yml`, `mise.toml` | the `agent-standards` pin |
| `package.json` | the `@webgrip/semantic-release-config` pin |

Every active repository's Dependency Dashboard issue is read once per scan: the open issue whose
title says *Dependency Dashboard* or whose body links Renovate's dashboard docs, since the title is
configurable (homelab-cluster's is *Renovate Dashboard 🤖*). It yields the counts of each dashboard
section and the verdict below. For a repository that is behind on a shared package the inventory
also reads its open pull requests and the combined commit status of the Renovate pull request it
picked (see [Is the update on its way?](#is-the-update-on-its-way)); a repository on the newest
release of every package costs no call beyond the dashboard.

`kind`, `branching` (staged or trunk), `core` and `GitHub mirror` come from the model
(`kubernetes/apps/repo-config/repo-config/model/repos.yaml`), not from the repository. Whether Renovate
is scheduled comes from the repository's topics: the `webgrip-forgejo` RenovateJob only discovers
repositories carrying the `renovate` topic.

### Series

| Series | Labels | Value |
| --- | --- | --- |
| `repo_config_repository_info` | `repository`, `kind`, `branching`, `core`, `github_mirror`, `renovate_gate`, `releases`, `ships`, `workflows`, `renovate_config`, `agent_standards`, `semantic_release_config`, `workflow_calls` | 1 |
| `repo_config_shared_latest` | `package`, `version` | 1 |
| `repo_config_shared_pin_releases_behind` | `repository`, `package` | stable releases newer than the oldest pin |
| `repo_config_shared_pin_unversioned` | `repository`, `package` | 1 when a pin has no version Renovate can read |
| `repo_config_shared_pin_update` | `repository`, `package`, `state`, `proposed`, `pull` | 1, for each behind pin |
| `repo_config_shared_pin_update_age_seconds` | `repository`, `package` | age of the Renovate pull request it found |
| `repo_config_workflow_call` | `repository`, `workflow`, `form` (`reusable` or `composite`) | 1 |
| `repo_config_scan_failed` | `repository` | 1 when its files could not be read |
| `repo_config_inventory_scan_failed_repositories` | | count |
| `repo_config_control_state` | `repository`, `state`, `fix`, `dashboard` | 1; one series per active repository |
| `repo_config_renovate_scheduled` | `repository` | 1 when it carries the `renovate` topic |
| `repo_config_renovate_dashboard_items` | `repository`, `section` | items listed in that Dependency Dashboard section: `problems`, `errored`, `pending_approval`, `awaiting_schedule`, `rate_limited`, `pending_status_checks`, `open` |
| `repo_config_renovate_dashboard_errors` | `repository` | Repository Problems lines that say `ERROR` |

The pin labels on `repo_config_repository_info` carry every version found, so a version bump starts
a new series. The board only reads series from the inventory's latest push, so a bump never shows
twice.

`AgentStandardsPinBehindForADay` warns when a repository's agent-standards pin stays behind for 24
hours without a break: the gates open that bump without a dashboard tick and merge it on green, so a
day behind means a pull request waits for an approval or a check, or the repository extends no gate.
agent-standards' own daily estate report reads the same organisation with this inventory's
read-only token, published to that one repository as `WEBGRIP_INVENTORY_TOKEN`.

### What the derived labels mean

- **renovate_gate**: `reviewed` or `unattended` for the gate the config extends;
  `presets` when it composes shared presets without a gate; `own` when it has a config with no
  shared preset; `none` without a config.
- **releases**, first match wins:

    | Value | Means |
    | --- | --- |
    | `monorepo (old path)` | a workflow calls `semantic-release-monorepo`, the composite action or the reusable workflow. This path is being retired; the board's *Repositories on the old release path* stat is the migration's finish line at zero |
    | `shared semantic-release` | a workflow calls the `semantic-release` composite action or reusable workflow of `webgrip/workflows` (since v4.0.0 it runs `webgrip-release` underneath) |
    | `webgrip-release` | a step runs the command itself: `node_modules/.bin/webgrip-release`, `node bin/webgrip-release.cjs`, or `webgrip-release` at the start of a `run:` line |
    | `own semantic-release` | a step runs `semantic-release` (or `knope release`) as a command |
    | `none` | none of these |

    Calls and steps in workflow files that are themselves reusable (`on: workflow_call`) are not
    counted, so the workflows library does not read as releasing or shipping everything it offers.
    Comment lines are skipped, and the toolchain image name does not count as running
    semantic-release.
- **ships**: `cloudflare`, `image`, `chart`, `npm` and `docs`, from shared workflow and composite
  action calls (`docker-build-push-registry-fast` and the other image builders read as `image`) and
  well-known publish steps (`wrangler deploy`, `docker/build-push-action`, `helm push`,
  `npm publish`). A repository that publishes some other way reads as `nothing`.
- **pin cells**: every version found, oldest first, then `· N behind` when the oldest is N stable
  releases behind. Following ADR-0089, a call is versioned when it is `@vX.Y.Z` or
  `@<40-hex sha> # vX.Y.Z`; a bare SHA, `@main` or `@<sha> # main` is `unversioned`, as is a preset
  without `#vX.Y.Z`. Renovate cannot move those. A tooling repository calling itself (the workflows
  repository's own `@main` calls) is not a pin, as in `scripts/check-tooling-pins.sh`.
- **semantic-release-config pin**: the `@webgrip/semantic-release-config` version in `package.json`
  and the tag of `harbor.webgrip.dev/webgrip/semantic-release:<version>` in a `container:`,
  `image:` or `toolchain-image:` line. Most consumers take the config through that image, whose tag
  is the config version it carries. Image tags below 1.0.0 belong to the retired 0.x image line,
  whose tags were never config versions, and are ignored rather than shown as a very old pin.

## Estate control: is a repository under control?

The first screen carries one verdict per active repository: the first check below that fails, with
the fix in words and a link to its Dependency Dashboard. *Repositories under control* is the share
that passes every check or is opted out.

| Verdict | Means | Fix |
| --- | --- | --- |
| unread | the inventory could not read its files, or its issues (the token needs `read:issue`) | the CronJob log names the read |
| opted out | the model says `renovate: absent: true` | nothing; it is a decision |
| no renovate | no Renovate config in any of the files above | add one that extends `reviewed` or `unattended` |
| not scheduled | a config but no `renovate` topic, so the RenovateJob never runs on it | add the topic |
| no dashboard | scheduled, but no Dependency Dashboard issue: Renovate has not finished a run | check the repository on the Renovate operator board |
| renovate errors | Repository Problems lists an `ERROR` line, or the Errored section is not empty | read the dashboard |
| parked | updates wait for a tick on the dashboard | with no gate preset (`reviewed`, `unattended`, or a `profile-*` alias of one) every update its own rules do not release waits, because `renovate-config`'s default preset requires approval for all of them: extend a gate, or tick them. Under a gate, majors, container and CI action updates and the always-review list wait by design: tick or close them |
| drifting | a shared pin is unversioned, or three or more stable releases behind | add the `# vX.Y.Z` comment or tag, or merge its Renovate pull request |
| under control | none of the above | — |

`ForgejoRepositoryOutsideRenovate` fires when a repository sits in no renovate, not scheduled, no
dashboard or renovate errors for six hours: those are the states where nothing updates the
repository and no pull request says so. parked and drifting do not alert; they are a person's queue,
and the board is where it is read.

## Is the update on its way?

The table *Behind a shared package: is the update on its way?* has one row per repository and shared
package whose pin is behind the newest stable release. The inventory reads the repository's open
pull requests and keeps the Renovate ones (head branch `renovate/…`). From each it reads which shared
package it moves and to which version: first from the version table Renovate writes in the
description (``| [webgrip/workflows](…) | … | `v3.4.0` → `v3.5.1` |``), else from the title
(`update dependency webgrip/agent-standards ( v0.5.3 ➔ v0.6.1 )`, `… to v4.0.0`). It knows these
dependency names: `webgrip/workflows`, `webgrip/renovate-config`, `webgrip/agent-standards`,
`@webgrip/semantic-release-config` and `harbor.webgrip.dev/webgrip/semantic-release`. When several
pull requests move the same package (a `3.x` and a `4.x` branch), the one to the newest version
counts.

| `state` | Board says | Means | Who acts |
| --- | --- | --- | --- |
| `pr_green` | PR open, checks green | the combined commit status is success | whoever merges, or Renovate under an unattended gate |
| `pr_red` | PR open, checks red | the combined status is failure or error | someone fixes the repository or the release, or closes the pull request |
| `pr_pending` | PR open, checks running | the status is pending, or no check reported yet | nobody yet |
| `awaits_approval` | waits for a dashboard tick | no pull request; the Dependency Dashboard lists it under *Pending Approval* | a person ticks it |
| `queued` | Renovate opens it soon | no pull request; the dashboard lists it as rate-limited, awaiting schedule or pending status checks | Renovate |
| `no_pr` | no update PR | neither a pull request nor a dashboard line | look at the repository's Renovate config and the renovate-operator jobs |

`proposed` is the version that pull request or dashboard line moves to, which can be short of the
newest release. `pull` is the pull request number. A repository whose pull requests cannot be read
keeps its pins but gets no update row; the CronJob log names it.

`SharedPackageUpdateRedForADay` warns when a row stays `pr_red` for the same pull request and
version for 24 hours without a break.

### From release to pull request

*From a shared release to the consumer's Renovate PR* measures how long consumers wait for Renovate
after a shared package releases: the creation time of each Renovate pull request minus the creation
time of the release it moves to, per package, over 30 days and over the last 7. It reads Forgejo's
database, not the inventory, so merged pull requests count too (the inventory only sees open ones,
which would leave out exactly the fast ones). The package and version come from the version table
in the pull request's description, so grouped `renovate/webgrip` pull requests count. A pull request
Renovate rewrote to a release newer than the one it was opened for is left out, because it was
opened before that release. Since `renovate-trigger` schedules Renovate on the consumers right after
a tooling release (2026-11-01), the 7-day column is the one to watch.

## Why one shared release turns into several pull requests

A release of a shared package reaches each consumer as a Renovate pull request in that repository.
Three of them do not share a branch on purpose:

| Branch | Holds | Why it is separate |
| --- | --- | --- |
| `renovate/webgrip` (*webgrip dependencies*) | minor, patch and digest updates of everything webgrip publishes: `webgrip/workflows`, `@webgrip/*`, Harbor and GHCR images | this is the one grouped first-party pull request; Renovate titles it after the dependency when only one is in it |
| `renovate/webgrip-renovate-config-*` | the `renovate-config` preset pin | a preset bump changes how Renovate treats the repository, not what it ships: it lands as `chore(renovate)`, cuts no release, is never digest-pinned and merges itself even where the gate holds everything else |
| `renovate/agent-package-*` | one agent package (`agent-standards`, …) | the bump runs `agentstd install` as a post-upgrade task, and Renovate takes a branch's task from its first update, so each package needs a branch of its own to install with its own tag |

Majors of webgrip packages open their own pull request and wait for a person. Third-party updates go
to their own group (`all non-major dependencies`) under the repository's gate. The rules live in
`renovate-config`: `first-party.json`, `apm.json` and `parts/agent-package-group.json`.

The *Renovate pull requests per upstream* table counts this fan-out over 30 days, and *Time to merge
per repository* shows which gate holds it.

## Reading the bottleneck queue

Each open pull request gets one state, first match wins:

| State | Meaning | Who acts |
| --- | --- | --- |
| red checks | the newest run of some workflow failed on the PR head | the author, or close it |
| checks running | a run is waiting or running | nobody yet |
| no checks ran | the repository runs no CI on pull requests | a person must judge it |
| automerge due | Renovate PR with the `automerge` label and green checks | Renovate, on its next run |
| approved, not merged | an official approval and green checks | whoever merges |
| waiting for review | green checks, no approval | a reviewer; core repositories need a second person (ADR-0083) |

*Updates waiting for a dashboard tick* reads each repository's Dependency Dashboard issue. It is as
fresh as Renovate's last run on that repository, which the table shows.

## Changing it

Edit `scripts/dashboards/delivery.py`, then run `python3 scripts/dashboards/generate.py`. For a new
pin, file or verdict, change the inventory and its suite: `sh scripts/test-repo-config-inventory.sh` runs the
tests and a mutation check against each behaviour.
